# Главный кирпич

## Какие сущности уже видны

- Document identity, conversation и Codex thread mapping.
- Turn, attempt, progress event и diagnostic.
- Context snapshot, selection set, model reference и fingerprint.
- TaskPlan, operation, value/expression, geometry reference и declared assumption.
- Capability definition и policy.
- Prepared change, commit journal и execution result.
- Rhino-owned object.
- Grasshopper component state, input, output и algorithm.
- Settings, account/model status и runtime installation.

Унифицировать все эти данные одним универсальным object/value bag нельзя без потери типобезопасности именно на границе, где она важнее всего.

## Вариант A — один кирпич: OperationNode

Каждая геометрия, input, ссылка и действие становится узлом:

- id;
- kind;
- typed properties;
- input node ids;
- result type;
- optional host.

**Выигрыш:** один walker для validation, prepare, C# rendering и execution; удобно строить DAG зависимостей.

**Проигрыш:** conversation, snapshot, account и commit journal искусственно превращаются в operations. Ошибки протокола смешиваются с геометрической семантикой, а универсальный property bag размывает compile-time проверки.

## Вариант B — два кирпича: OperationNode + EventEnvelope

### Кирпич 1. OperationNode

Детерминированный узел canonical operation graph:

- nodeId;
- operationKind и schemaVersion;
- targetHost;
- typed operands/parameters;
- dependency node ids;
- expected result type;
- source plan operation id.

Варианты: create curve/surface/extrusion/Brep, transform, copy, boolean, layer/attributes, reference selected/owned geometry, GH input/expression/output.

### Кирпич 2. EventEnvelope

Неизменяемая запись жизненного цикла:

- eventId и correlationId;
- documentKey, conversationId, turnId, attemptNo;
- eventKind;
- timestamp;
- status/errorCode;
- redacted typed payload reference.

Варианты: user message, snapshot captured, Codex event, plan received/rejected, prepare completed, commit started/completed/rolled back, stop requested, transcript result.

**Выигрыш:** все геометрические способности получают общий graph pipeline, а UI/transcript/recovery — единый упорядоченный поток событий. Типизированные domain records (snapshot, settings, component state) остаются отдельными и не маскируются универсальным blob.

**Проигрыш:** нужны две схемы версионирования и явное отображение transient EventEnvelope на persisted transcript/journal. Это приемлемая цена за разделение intent и lifecycle.

## Вариант C — без унификации

Каждая operation, event и state имеет отдельный класс и собственный pipeline.

**Выигрыш:** максимальная локальная типобезопасность и простые DTO в начале.

**Проигрыш:** validator, C# renderer, executor, retry diagnostics и UI reducer быстро обрастают switch-логикой; одинаковые гарантии разных capabilities начинают расходиться.

## Решение

**Подтверждён вариант B: OperationNode + EventEnvelope.** Два кирпича соответствуют двум независимым осям системы:

1. что нужно вычислить и применить — OperationNode;
2. что произошло с запросом — EventEnvelope.

TaskPlan остаётся внешним недоверенным DTO и после validation компилируется в canonical graph. Snapshot, settings, runtime state и serialized GH component state остаются отдельными типизированными сущностями.

## Canonical graph specification

- Graph является immutable DAG после compilation.
- Stable topological sort использует dependencies, затем nodeId как tie-break.
- Все defaults материализуются явно; implicit unit, plane, tolerance и coordinate system запрещены.
- Числа сериализуются invariant round-trip format; physical values заранее нормализуются в document units с сохранённой source unit.
- Canonical JSON задаёт фиксированный порядок properties и discriminated operand variants.
- graphHash включает TaskPlan schema, registry/capability versions, target host, units/tolerances, node graph и fingerprints разрешённых references.
- Native multi-result outputs сортируются по stable geometry signature до назначения result ids; output order RhinoCommon не считается стабильным.
- Validator, C# renderer и executor читают один immutable graph и не вычисляют независимые defaults.

Golden/parity tests проверяют одинаковые graphHash, C# representation и geometry signatures при повторе, другой culture и разных порядках JSON properties.
