# Методологии

## 1. Typed plan → validation → controlled execution

Модель формирует не исполняемый C#/Python, а строгий TaskPlan. JSON Schema проверяет форму, семантический валидатор — права на объекты, типы, единицы, лимиты сложности и допустимые операции. Исполнитель переводит прошедший план в RhinoCommon или состояние одного GH-компонента.

## 2. Ограниченный plan–act–observe–repair

После исполнения RhiGhAI собирает структурированный результат или ошибку, откатывает неудачную попытку и просит Codex исправить план. Цикл ограничен настройкой 1–5; auth, лимит и ручная остановка не повторяются.

## 3. Долгоживущий диалог, свежий снимок модели

Codex thread хранит смысл разговора, но каждое действие получает новый компактный снимок единиц, слоёв, выделения, владельцев и host target. История не заменяет проверку текущего состояния.

## 4. Редактируемый артефакт

Rhino-результат остаётся нативной геометрией. Grasshopper-результат — живой RhiGhAI Parametric с типизированными входами и воспроизводимым алгоритмом, а не одноразовый bake.

## 5. Optimistic concurrency

Перед применением сохраняется fingerprint релевантных объектов и документа. На UI-потоке он проверяется повторно; устаревший план не применяется.

## 6. Prepare in memory → short atomic commit

Долгая работа Codex и подготовка геометрии идут вне Rhino-транзакции. На UI-потоке остаётся короткий commit под одним undo record. Это поддерживает отзывчивость и делает откат реалистичным.

## 7. Тонкая нативная интеграция

Плагин не становится универсальным роутером инструментов и не строит собственный CAD kernel. Он содержит небольшой реестр проверенных операций, адаптер Codex app-server и два host-исполнителя.

Эти подходы превращают принципы [[what-to-steal]] в проверяемую архитектуру и ограничивают риски из [[what-to-avoid]].
